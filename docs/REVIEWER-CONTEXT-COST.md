# Reviewer 上下文与费用：2026-09-06 检查

## 它没有读取主模型全部上下文

当前实现为每个审查动作创建独立 reviewer session，给予固定系统规则、
策略检索工具，以及一个限额内的动作证据包，不直接复用主 Agent session：

- 当前工具名称、参数、路径、预期副作用、沙盒边界、权限策略。
- 从真正的用户消息中提取的当前要求，最多 8192 字符；不是把工具输出当用户授权。
- 有界的最近用户、助手公开文本和工具证据，带可信来源标签。
- 与具体动作绑定的授权和摘要，不把一次允许扩展为任意命令通行证。

router 当前最多产生 12 条历史证据，每条最多 4096 字符。
provider 再按配置的条数、字节预算裁剪（默认 12 条、32768 bytes）。
把设置的条数调到 12 以上，目前不会扩大 router 的 12 条上限。
初始 JSON 证据包另受 maxInputBytes 限制；这不是模型完整输入的 token 上限：
系统规则、工具 schema、策略查询返回和后续 reviewer 轮次仍会计费。

本次修复两个实质问题：

1. 原 contentText 会取任何带 text 的内容块，包括 reasoning。现在显式过滤
   reasoning / thinking 类型；旧版不能声称完全没有传递这些片段。
2. 原先先检查 12 条上限，再提取用户要求。工具密集时可能漏掉真正的当前要求。
   现在把授权提取与 transcript 条数独立处理，并加入双版本 session API 回归。

过滤的是结构化私有推理块，不是假设能从普通公开文本中识别所有“思考句子”。
Reviewer 没有主 Agent 的 Shell 工具集，也没有自主无限读取主会话的能力。

## 为什么缓存比主模型低

reviewer 输入缓存命中率为 55.96%；主编码任务为 97.02%。
这两个比例来自不同负载，不能直接判定 reviewer 实现落后。

源码证据：

1. 主编码对话通常追加历史，大段前缀可复用；审查是独立动作证据包。
2. actionId / actionDigest 很早出现在 JSON 中，动作一变就打断后面的公共前缀。
3. 工具参数、当前用户授权、最近历史、策略搜索页均会变化。
4. 样本仅 4 次审查，包含冷启动和两次失败成本，无法代表长期稳定命中率。

DeepSeek 缓存匹配已持久化的完整前缀单元，不是匹配任意重复文本。
公共前缀还需被检测和持久化，缓存构建有延迟，命中不是保证。
来源：[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。

优先改进方向（除推理块过滤外，尚未做收益 A/B）：

- 固定 system / schema / 序列化顺序，把稳定政策放前面、动作唯一标识放后面；
  不删除绑定字段，不复用过期授权。
- 先做桥接能力与制品可用性检查，再花 reviewer 模型费用。
- 控制策略分页与重复查询，保留必要原始授权和风险证据。
- 分别统计缓存命中输入、未命中输入、输出与重试费用。不能为了好看的命中率
  填充无用上下文，也不能为减少模型费用降低沙盒或审查覆盖。

## 主模型 100 万 tokens 时，reviewer 大约多少

没有固定比例。主模型总输入包含大量重复历史，不等于新生成 100 万 tokens，
也不能推出工具调用次数。更有意义的公式：

```text
Reviewer 总成本 = Σ 每个审查动作的所有调用成本（包括策略检索、重试和失败）
```

上述小样本每次审查约 6k–15k 总 tokens，仅供容量规划：

| 需要审查的动作数 | 估算 reviewer 总 tokens |
| ---: | ---: |
| 0 | 0 |
| 2 | 12k–30k |
| 5 | 30k–75k |
| 20 | 120k–300k |

这些是情景估算，不是“每百万主模型 tokens 必然发生这么多次审查”的预测。
应同时报告每百动作审查次数、每次审查成本、失败成本和完成任务的实际账单。
